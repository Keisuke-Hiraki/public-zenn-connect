AWS IAM Identity Center（以下 IIC）のマルチリージョンサポートは、2026 年 2 月に外部 IdP（Okta や Microsoft Entra ID など）を接続している組織インスタンス向けにまず発表されていました。

https://aws.amazon.com/jp/about-aws/whats-new/2026/02/aws-iam-identity-center-multi-region-aws-account-access-and-application-deployment/

そして 2026 年 7 月 29 日、この対象が Identity Center directory を ID ソースとするインスタンスにも拡大されました。外部 IdP を使わない、いわゆる素の IIC 環境でも同じ耐障害性のメリットを受けられるようになった、というのが今回のアップデートです。

https://aws.amazon.com/jp/about-aws/whats-new/2026/07/aws-iam-identity-center-extends-multi-region-support-to-identity-center-directory/

「マルチリージョンにサポートしました」というだけの機能アップデートに見えますが、個人的には少し違う受け止め方をしています。認証基盤の可用性は、便利機能の話ではなく、セキュリティ対策そのものだと思っているからです。今回はその視点も交えて、マルチリージョン対応の仕組みと効果を見ていきます。

- 利用には組織インスタンス・マルチリージョン対応の customer managed KMS キーなどの前提条件がある
:::

## なぜ認証基盤の可用性が「セキュリティ対策」なのか

セキュリティというと機密性（Confidentiality）や完全性（Integrity）が思い浮かびがちですが、CIA トライアドにはもう一つ「可用性（Availability）」があります。  
IIC のような認証・アクセス基盤にとって、この可用性は特に重い意味を持ちます。IIC が使えなくなるということは、単に不便になるだけでなく、AWS アカウントへのアクセスそのものが止まる、つまりインシデント対応に入ろうとしてもログインできない、という状況を意味するからです。

この課題については、以前にも記事で取り上げました。  
2025 年 10 月に発生した us-east-1 の大規模障害では IIC も影響を受け、ログインできない状況が発生しました。そうした事態に備えて緊急時アクセス手順（Break-Glass Access）を用意しておく重要性を紹介した記事です。

https://zenn.dev/cscloud_blog/articles/idp-break-glass-access

Break-Glass Access は「認証基盤そのものが機能しない場合に、通常の経路を迂回して最小限のアクセスを確保する」ための備えです。

一方で今回紹介するマルチリージョン対応は、「そもそも認証基盤自体を複数リージョンで冗長化しておく」というアプローチであり、両者は補い合う関係にあります。

単一リージョン依存のリスクは AWS に限った話ではありません。

他クラウドの事例として、Microsoft Azure では 2024 年 7 月 30 日、DDoS 攻撃への対処に起因して Azure Front Door や Azure CDN で接続障害が発生しました。この障害により、Azure ポータルをはじめとする複数サービスに約 8 時間影響が及んだ事例が公開されています。

https://azure.status.microsoft/en-us/status/history/?trackingId=KTY1-HW8

この事例が示しているのは、特定ベンダーの優劣ではなく、「管理コンソールやポータルが単一リージョン（あるいは単一の経路）に依存していると、そこに障害が発生した瞬間にアクセス手段そのものを失いかねない」という一般的な構造です。認証基盤やアクセスの入口が一箇所に集中している限り、このリスクはどのクラウドでも起こり得ます。だからこそ、ID 基盤自体を多重化しておくことに意味があります。

## 何がアップデートされたか

改めて経緯を整理すると、IIC のマルチリージョン対応そのものは 2026 年 2 月に発表された機能で、当初は外部 IdP を接続している組織インスタンスのみが対象でした。

今回のアップデートのポイントは、この対象が「Identity Center directory を ID ソースとする場合」にも広がったことです。

- 対応リージョン: 17 のデフォルト有効な商用 AWS リージョン（オプトインリージョンは対象外）
- 対象外: Active Directory を ID ソースとしている場合は、引き続きマルチリージョン対応の対象外
- 料金: IIC 自体の利用に追加コストはなし。ただしマルチリージョン対応の customer managed KMS キーを使うため、AWS KMS の通常料金は発生する

## マルチリージョンの仕組み

IIC の組織インスタンスを有効化する際、最初に選んだリージョンが「プライマリリージョン」になります。そこに任意の「追加リージョン」を追加すると、以下のデータがプライマリリージョンから自動的にレプリケーションされます。

| データ | レプリケーション元 → 先 |
| --- | --- |
| ワークフォース ID（ユーザー、グループ、グループメンバーシップ） | プライマリ → 追加リージョン |
| 権限セットとユーザー・グループへの割り当て | プライマリ → 追加リージョン |
| 設定（外部 IdP の SAML 設定など） | プライマリ → 追加リージョン |
| アプリケーションのメタデータと割り当て | アプリが接続されているリージョン → 他の有効リージョン |
| Trusted token issuer | プライマリ → 追加リージョン |
| セッション | セッションの発生元リージョン → 他の有効リージョン |

レプリケーションは非同期で、結果整合性（eventual consistency）のモデルです。初回のレプリケーションはデータ量に応じて時間がかかりますが、以降の差分反映はほとんどの場合数秒以内に完了します。

プライマリリージョンで障害が発生した場合、ワークフォースは追加リージョンの AWS access portal エンドポイントに切り替えてアクセスを継続できます。これは、障害発生前に権限セットの割り当てなどが正しくレプリケーションされていることが前提です。なお AWS CLI の認可は各リージョンで個別に行う必要があり、レプリケーションの対象外である点は注意が必要です。

## セキュリティ対策としてどう効くか

ここが今回のアップデートの本質だと考えている部分です。マルチリージョン対応は、単に「アプリケーションのデプロイ先を選べる」という運用上の柔軟性だけでなく、認証基盤そのものの単一障害点を減らすという、セキュリティ・レジリエンスの観点で効果を持ちます。

プライマリリージョンで障害が発生しても、事前にレプリケーションされた権限情報を使って追加リージョンからアクセスを継続できます。これは、Azure の事例のように「ポータルへの入口そのものが止まる」状況に対する、AWS 側での現実的な備えの一つです。

ただし、この機能は Break-Glass Access の代替ではありません。マルチリージョン対応が守るのは「IIC 自体が正常に動作しているが、特定リージョンで障害が起きている」ケースです。IIC 自体が広域で機能しなくなるような、より深刻な事態に対しては、依然として Break-Glass Access のような迂回手段が必要です。両方を組み合わせることで、初めて認証基盤に対する多層防御が成立します。

つまり、今回のアップデートは「試してみると便利な新機能」ではなく、「認証基盤のレジリエンス設計の一部として検討すべき対策」として捉えるのが適切だと考えています。

## 利用にあたっての前提と注意点

導入を検討する際は、以下の前提条件と注意点を押さえておく必要があります。

- **インスタンスタイプ**: 組織インスタンスのみが対象。アカウントインスタンスでは利用できません
- **ID ソース**: Identity Center directory または外部 IdP のみ対応。Active Directory を ID ソースにしている場合は利用できません
- **KMS キー**: IIC の暗号化にマルチリージョン対応の customer managed KMS キーを設定している必要があります。同じ AWS アカウント内に配置する必要があります
- **リージョン**: デフォルト有効な商用リージョンのみが対象。オプトインリージョンは現時点では非対応です
- **リージョン数のクォータ**: 追加できるリージョン数には上限があります
- **リージョン削除時の注意**: 追加リージョンを削除しても、そのリージョンに接続された AWS 管理アプリケーションのデプロイが残っていると課金が継続する場合があります。削除前にアプリケーション側でのデプロイ解除を済ませておくことが推奨されています

:::message alert
既存の AWS 管理アプリケーションが customer managed KMS キーでの構成、および追加リージョンへのデプロイをサポートしているか、事前に確認しておく必要があります。
:::

## まとめ

IAM Identity Center のマルチリージョン対応が Identity Center directory にも拡大されたことで、外部 IdP を使わない環境でも同じ耐障害性のメリットを受けられるようになりました。

大事なのは、この機能を単なる「新機能だから試してみる」ものとして扱うのではなく、認証基盤の可用性、つまりセキュリティのレジリエンス設計の一部として検討することだと思います。Break-Glass Access のような迂回手段と組み合わせることで、認証基盤に対する備えがより強固になります。
