## 調査を依頼する前に考えておきたいこと

たとえば EDR のアラートをきっかけに、ファイルサーバーが外部と不審な通信をしているとわかったとします。すぐにでも調査を頼みたくなりますが、何を明らかにしたいのかを決めないまま始めると、報告書が届いてから「知りたかったことが書かれていない」となりがちです。ユーザー向けチェックリストの前半は、こうした食い違いを防ぐために、調査を始める前にベンダーと合意しておく事項をまとめたものです。

依頼の前に合意しておきたい主な事項は、次の 5 つです。

- **調査の目的と結果の使い道**：侵入経路の特定、情報漏えいの有無の確認、封じ込めや復旧の支援など
- **優先する事項**：復旧と調査のどちらを先にするか
- **判断できない可能性がある事項**：その原因、結果への影響、追加調査で補えるか
- **調査の範囲と手法**：対象のシステム、ログ、期間と選んだ理由、手法ごとにわかることとわからないこと
- **報告の受け取り方**：報告書に含める項目、報告の時期と速報の条件、報告書の共有先

目的によって、集める証拠も調べる範囲も変わります。結果を被害公表や監督官庁、保険会社への説明に使うなら正式な報告書が要りますが、確認したいことがはっきりしていて用途が決まっていなければ、口頭説明や簡易報告で足りることもあります。

優先する事項では、復旧と証拠保全のトレードオフを考えることになります。復旧を急いでシステムを再構築すると、調査に必要な証拠が消えることがあります。反対に、調査を優先すれば業務の再開は遅れます。どちらを取るかは、業務への影響、証拠保全への影響、調査にかかる期間について説明を受けたうえで判断します。

判断できない事項を先に聞いておくのは、調べてもわからないことがあるからです。ログの保存期間が短かったり、必要な監査設定が無効だったりすると、調査を進めても侵入経路や情報漏えいの有無がわからないことがあります。先に聞いておけば、報告書に「判断できない」と書かれていても、次に何をするかを考えやすくなります。

手法についても同じで、たとえばディスクフォレンジック（ディスクの複製から、ファイルの作成や削除、プログラムの実行履歴を調べる手法）でも、ファイルが削除されていると特定できない場合があります。

報告書には少なくとも、エグゼクティブサマリー、初期侵入の原因、影響範囲、被害内容、再発防止策の 5 つを含めるよう合意します。速報は、新たな侵害対象が見つかった場合や、情報漏えいの評価が変わった場合に受けられるようにしておきたいところです。報告書を取引先や保険会社に渡す可能性があるなら、共有先と第三者提供の可否もこの段階で伝えます。

こうした合意は、口頭で済ませずにメールなど記録が残る形で受け取るよう、チェックリストでも勧めています。調査が長引くと認識がずれやすいので、地味ですが後で認識を合わせ直すときに役立ちます。

## 調査報告書のどこを確認するか

調査が終わると報告書が届きます。ただ、たとえば「このサーバーに侵害の痕跡は確認されなかった」と書かれていても、それだけで安全と判断できるわけではありません。どこまで調べた結果なのか、何を根拠にしているのかまで読む必要があります。

ユーザー向けチェックリストの後半は、届いた報告書のレビュー項目です。報告書に何が書かれているべきかを示したものなので、それぞれの情報を被害組織が何の判断に使うのかを、筆者なりに整理すると次のようになります。

| 精査する情報 | 判断に活用する場面 |
| --- | --- |
| 発覚日時、検知のきっかけ、初動対応の履歴 | 調査期間と証拠保全の対象が妥当だったかの確認 |
| 侵害が確認された、または疑われるシステム・アカウント | 封じ込めの対象と追加調査の範囲の決定 |
| 取得できたログ、欠損したログ、調査対象外の範囲 | 結論の信頼性と追加調査の必要性の評価 |
| 外部通信、アクセスされたデータ、操作履歴 | 情報漏えいの可能性と影響範囲の評価 |
| 調査結果と証拠の対応関係 | 結論の妥当性と、社内外に説明できるかの確認 |
| 残存リスク、再発防止策とその優先度 | 復旧や対応の順序の判断 |

この中で特に気をつけて読みたいのが、結論の書き方です。チェックリストは、調査した各システムへの侵害について、次のどれに当たるかを明示するよう求めています。

| 結論の区分 | 意味 |
| --- | --- |
| 侵害を確認した | 調査で侵害の事実を確認した |
| 侵害の痕跡は確認されなかった | 調べた範囲とログの中では、侵害の跡が見つからなかった |
| ログ不足などにより判断できない | 評価するための材料が足りなかった |

2 つ目と 3 つ目は似ていますが、2 つ目は調べたうえでの結果で、3 つ目は調べる材料が足りなかったという状態です。ただし 2 つ目も、調べた範囲の中で見つからなかったという意味なので、**侵害されていないことの証明にはなりません**。被害公表や取引先への説明では、この違いがそのまま説明の中身に関わってきます。

なお、情報漏えいの評価は別の区分で、「漏えいを確認した」「漏えいした可能性がある」「漏えいを示す痕跡は確認されなかった」「判断できない」の 4 つです。

結論の根拠をたどれるかも見ておきたい点です。報告書サンプルでは、取得したログやディスクイメージに「E-101」のような証拠 ID が振られ、それぞれの調査結果にどの証拠を使ったかが書かれています。直接の証拠がない推測は、推測だとわかる書き方になっているかも見ます。こうした対応がとれていれば、後から結論を見直すときや、別のベンダーに再調査を頼むときにも困りません。

もう一つ、実務で使いやすいのが IoC（Indicator of Compromise）の一覧です。攻撃に使われた IP アドレスやドメイン、ファイルのハッシュ値など、侵害の痕跡を示す情報のことで、自社のログ検索や監視に使えます。報告書の中では誤アクセスを防ぐため `example[.]com` のような defang 形式で書かれるので、テキストや Excel で別に受け取ると取り込みやすくなります。

## 報告書サンプルに見る「判断できない」の書き方

結論が実際にどう書かれるかは、[報告書サンプル（PDF）](https://jpcertcc.github.io/ir_report_checklist/pdf/incident_forensic_report_template_ja.pdf)を読むとイメージしやすくなります。架空の組織を対象にした報告書で、ファイルサーバーから外部への通信を EDR が検知して発覚した、という設定です。報告書では、攻撃者は VPN 装置を経由して侵入した可能性が高いと評価されています。その後、管理者アカウントなどが悪用され、AD サーバーやファイルサーバーにアクセスされたことは確認されています。

この報告書は、侵入の方法を断定していません。VPN 装置の脆弱性が悪用されたのか、認証情報が悪用されたのかのどちらかだとしたうえで、断定できない理由として次の 2 点を挙げています。

- VPN 装置のログがローテーションで消え、調査期間より前の分が残っていなかった
- 不審な接続の前後のクラッシュログが残っていなかった

このほか、AD サーバーでは監査ポリシーが十分に有効になっておらず、プロセスの実行やコマンドライン、ログオン失敗などの一部のイベントが記録されていなかったことも、調査上の制約として書かれています。

ログは保存期間だけでなく、何を記録していたかによっても調べられる範囲が変わる、ということがよくわかる例です。サンプルの注記には、侵入時期がわからない場合の調査の目安として、発見時点から少なくとも数か月から 1 年程度さかのぼってログを調べる必要があるとも書かれています。

情報持ち出しの評価も参考になります。サンプルでは、ファイルサーバーで次のことが確認されました。

- 共有フォルダのファイル一覧を取得するコマンドが実行された
- ファイルシステムの管理情報（MFT）に、RAR ファイルの名前の痕跡が残っていた
- 同じ日の夜に `sftp.exe` が実行された
- ファイアウォールのログに、約 2 時間半の間に約 176MB の外部送信が記録されていた

一方で、RAR ファイル本体は見つかっていません。通信も暗号化されていて、送られたファイルの中身はわかりません。

報告書はこれらの事実を合わせて、情報が持ち出された「**可能性がある**」と評価しています。そのうえで、一覧が取られたフォルダのファイルを、影響を受けたデータの範囲を確認する資料として別紙にまとめています。直接の証拠がなくても、確認できた事実を並べて確度つきで評価し、影響範囲の候補まで示す書き方です。

## 調査結果を受けてどう判断・対応するか

報告書が届いたら、その内容をもとに封じ込めや復旧、追加調査を決めていくことになります。ここからは、チェックリストと報告書サンプルを読んで筆者が考えたことです。サンプルにもとづく部分は、そうとわかるように書いています。

**侵入原因が断定できない場合**

侵入原因が断定できなくても、再侵入を防ぐ手は打てます。先ほどのサンプルでも侵入方法は絞り込めていません。それでも推奨対策には、VPN 装置のファームウェア更新と管理画面のアクセス制限に加えて、VPN アカウントと特権アカウントへの MFA 適用が、どちらも優先度「高」で並んでいます。脆弱性の悪用と認証情報の悪用の両方に備える形です。原因の候補が複数あるなら、候補ごとに塞ぐ対策が挙がっているかを見るとよいと思います。

**侵害の有無を判断できないシステムがある場合**

判断できなかったシステムは、まず追加調査で確かめられるかを考えます。サンプルでも、一部のサーバーは必要なデータだけを素早く集めて調べるファストフォレンジックしか実施していないため、必要に応じて再構築前に追加のディスクフォレンジックを行うよう勧めています。追加調査が難しい場合や時間をかけられない場合は、侵害されている可能性を残存リスクとして扱い、認証情報のリセットや再構築、監視の強化といった予防的な対応を検討することになると思います。

**情報漏えいが疑われる場合**

情報漏えいの可能性がある場合、報告書からわかるのはデータの種類や保存場所、サンプルでいえばファイルの一覧までです。その中に個人情報や取引先の機密情報が含まれるか、個人データが含まれる場合に個人情報保護委員会への報告や本人への通知が必要か、公表するかは、データを扱う業務部門や法務、広報と一緒に評価することになります。

**封じ込め・復旧の完了判断**

封じ込めや復旧が終わったと判断するときは、報告書に挙がった侵害アカウント、ホスト、通信先のそれぞれに何をしたかを説明できるかが一つの目安になると思います。サンプルの対策表には「対応する調査結果」の列があり、各対策がどの調査結果にもとづくかが示されています。この対応をそのまま進捗管理に使えば、未実施の対策や、残存リスクとして受け入れた事項も整理しやすくなります。逆に、どの事案にも当てはまる一般的な対策しか並んでいなければ、調査結果との対応をベンダーに聞いてみるとよいでしょう。

なお、サンプルでは、優先度は対応順序の目安で、業務への影響まではすべて確認していないため、実施可否と手順は協議するよう注記されています。全認証情報のリセットやサーバーの再構築は業務を止めることもあるので、社内の担当部門とすり合わせながら進めることになります。

## 平時に準備しておきたいこと

報告書サンプルの例からもわかるように、調査で何がわかるかは、被害組織の手元に残っているログや情報にかなり左右されます。インシデントが起きてからでは用意できないものもあるので、筆者は次のような準備をしておきたいと考えています。

| 準備しておきたいこと | 準備がないと困る場面 |
| --- | --- |
| ログの保存期間と、ログオンやプロセス実行など記録するイベントの確認 | 侵入時期までさかのぼれない、必要な操作が記録されていない |
| 各システムの時刻同期と、ログのタイムゾーンの把握 | 複数のログを突き合わせてタイムラインを作りにくい |
| ネットワーク構成図、システム一覧、特権アカウント一覧の更新 | 調査対象や封じ込めの対象をすぐに決められない |
| 発覚時の記録の担当と方法、報告書を渡す可能性がある先の洗い出し | ヒアリングで正確に伝えられない、報告書の形式を決められない |

サンプルの再発防止策でも、侵入原因を断定できなかったことを受けて、VPN 装置のログを 1 年程度保存し、集中ログ基盤へ転送するよう勧めています。サンプルの事案に対する対策ですが、自社のログを見直すときの参考になります。

クラウドサービスや SaaS を使っている場合は、監査ログに何が記録され、どこに、どのくらいの期間残るかも確認しておきたいところです。レポーター向けのチェックリストでも、報告書に必要な項目が変わるインシデントの種類としてクラウド侵害が挙げられています。

たとえば AWS CloudTrail では、次の仕様を押さえておくと、どのログが残っているかを判断しやすくなります。

- [イベント履歴](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/view-cloudtrail-events.html)で確認できるのは、リージョンごとの過去 90 日間の管理イベント
- S3 のオブジェクト操作などの[データイベント](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/logging-data-events-with-cloudtrail.html)はイベント履歴に含まれず、証跡や CloudTrail Lake のイベントデータストアでも既定では記録されない
- 長く残すには証跡や CloudTrail Lake を設定し、調査で必要になりそうなデータイベントは、追加料金も考えたうえで記録の対象に加える

## まとめ

JPCERT/CC のインシデント調査報告書チェックリストを、調査を依頼する被害組織の立場から読んでみました。

読んでいて感じたのは、調査報告書は受け取って終わりではなく、その後の判断の材料だということです。そのためには、依頼の段階で目的と範囲を決めておき、届いた報告書では結論が「確認できた」「可能性がある」「判断できない」のどれで、何を根拠にしているかを確かめることになります。判断できなかった事項も、残存リスクとして扱えば、追加調査をするか予防的な対応を取るかを決める材料になります。

そして、何が判断できるかは、手元に残っているログで決まる部分が大きいです。ユーザー向けのチェックリストは分量も多くないので、平時に一度読んで、自社のログの取得状況や報告先と照らし合わせておくと、いざというときに慌てずに済むと思います。
