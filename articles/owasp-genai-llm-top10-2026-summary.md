## OWASP Top 10 for LLM Applications とは

OWASP GenAI Security Project が公開している、LLM を組み込んだアプリケーションで発生しやすいセキュリティリスクを 10 個にまとめたリストです。2023 年 8 月の v1.0 リリース以降、2025 年 11 月の 2025 年版を経て、今回 2026 年版が公開されました。

これまでのバージョンは、開発者・データサイエンティスト・セキュリティ実務者数百人の投票による合議制で作られていました。今回はこれに加えて、公開されている脆弱性データベースと AI 被害データベースから集めた 7,714 件の実インシデントを分類器で読み込み、6,639 件を実際に分析対象として使うという、根拠に基づくアプローチが初めて導入されています。

投票の重みを 75%、インシデント分析の重みを 25% とすることで、コミュニティの経験に基づく判断を土台にしつつ、実際に起きたことで検証するという二段構えになっています。プロジェクトリードの Letter によると、この 2 つは常に一致するわけではなく、その食い違い自体が今回の順位変動に強く影響しています。

:::message
この記事の対象は「モデルがアプリケーションの一部品（コンポーネント）として動く」ケースです。モデルがツールを自律的に呼び出し、セッションを超えて記憶を持ち、その結果が下流に影響を与える「エージェント」として動くケースのリスクは、姉妹プロジェクトの `OWASP Top 10 for Agentic Applications`（ASI、2025-12-09 発表）が担当します。この記事内でも該当箇所で ASI 側の項番を参照します。
:::

## 2025 年版からの変更点

まず全体の順位変動を見てみます。

| 2026 年版 | リスク名 | 2025 年版での順位 | 変動 |
|---|---|---|---|
| LLM01 | Prompt Injection | 1 位 | 変動なし |
| LLM02 | Sensitive Information Disclosure | 2 位 | 変動なし |
| LLM03 | Excessive Agency | 6 位 | ↑ 3 上昇（最大の上昇） |
| LLM04 | Supply Chain | 3 位 | ↓ 1 低下 |
| LLM05 | Data and Model Poisoning | 4 位 | ↓ 1 低下 |
| LLM06 | Unbounded Consumption | 10 位 | ↑ 4 上昇 |
| LLM07 | Misinformation | 9 位 | ↑ 2 上昇 |
| LLM08 | Hidden Context Exposure | 7 位（System Prompt Leakage） | 名称・範囲変更 |
| LLM09 | Vector and Embedding Weaknesses | 8 位 | ↓ 1 低下 |
| LLM10 | Improper Output Handling | 5 位 | ↓ 5 低下（最大の低下） |

上位 2 位（Prompt Injection、Sensitive Information Disclosure）は不動ですが、3 位以下は大きく入れ替わりました。特に注目したいのが以下の 3 点です。

**Excessive Agency の急上昇**が最も大きな変化です。エージェント型のデプロイで実際に被害が出ているという投票とインシデント記録が一致した結果で、6 位から 3 位まで上がりました。

**Prompt Injection が投票では 1 位のまま、生インシデント数だけで見ると Top 10 圏外**という食い違いも印象的です。Letter from the Project Leads では、これは「防御効果」だと説明されています。多くのチームがこのリスクに真剣に対策コストを割いているため、公開データベースに載るような分かりやすい悪用事例が少なくなっているだけで、攻撃面自体（モデルが未検証の入力を読むところ全て）は消えていないという解釈です。データを信じて順位を下げるのではなく、「対策されているからこそ表面化しにくい」というリスクの性質を踏まえて 1 位を維持しています。

**Misinformation は逆方向の食い違い**です。投票では下位でしたが、インシデント記録では上位に近い結果が出ました。モデルの流暢で自信を持った誤った出力がそのままツール呼び出しや意思決定に使われて実害につながるケースが記録上は多いということで、7 位まで上げられています。

**System Prompt Leakage → Hidden Context Exposure への改名**も見逃せません。単純な名前変更ではなく、システムプロンプトの漏洩だけでなく、ツールのスキーマ定義や RAG のポリシー文書など、モデルには見えるがユーザーには見えないよう設計された「隠されたコンテキスト」全般に対象が広がっています。

## LLM Top 10 2026 の全体像

公式ドキュメントでは、10 個のリスクを「攻撃がどこから入り、どう増幅され、どこに着地するか」という同心円状の図で整理しています。これに沿って分類すると以下のようになります。

| レイヤー | 該当リスク | 役割 |
|---|---|---|
| 侵入経路（Entry Vectors） | LLM01 Prompt Injection、LLM04 Supply Chain、LLM05 Data and Model Poisoning | 攻撃者がシステムに最初に接触する経路 |
| 増幅機構（Amplifiers） | LLM08 Hidden Context Exposure、LLM09 Vector and Embedding Weaknesses | 侵入した攻撃の効果を広げる仕組み |
| 中核的な被害（Core Impacts） | LLM02 Sensitive Information Disclosure、LLM06 Unbounded Consumption、LLM07 Misinformation | 最終的に発生する実害 |
| 被害への直接経路 | LLM03 Excessive Agency、LLM10 Improper Output Handling | 侵入経路から中核的な被害へ直接つながる経路 |

「攻撃は内側に向かって流れ、防御は外側に向けて押し返す」という一文が図に添えられています。1 つのリスクに対処すれば終わりではなく、侵入経路・増幅機構・被害という 3 層それぞれに防御を積む多層防御の発想が前提になっている点は、他の OWASP Top 10 シリーズと共通する考え方です。

## 各リスクの解説

ここから 10 個のリスクをそれぞれ見ていきます。各項目は「Description（概要）」「Common Examples of Risk（典型的な発生パターン）」「Prevention and Mitigation Strategies（対策）」の構成になっているため、それに沿って要点を絞って紹介します。

### LLM01:2026 Prompt Injection

LLM に渡される入力（直接入力・検索結果・ツール出力・画像や音声・記憶）が、開発者の意図しない形でモデルの振る舞いを変えてしまう問題で、2025 年版から続けて 1 位です。

LLM は「指示」と「データ」を区別できるアーキテクチャを持っていません。両方とも同じトークン列として処理されるため、SQL のプレースホルダのような確実な防御策が原理的に存在しません。攻撃はユーザーが直接入力する **Direct Injection** と、Web ページや文書、ツールの応答など外部コンテンツ経由で届く **Indirect Injection** に分かれ、Indirect Injection はさらに「信頼されていない経路」「準信頼経路（バグトラッカーのタイトルなど）」「信頼された経路（開発者自身のリポジトリ）」に分類されます。ユーザー自身の LLM インスタンスが自分自身のバックエンドへの攻撃ツールに転用されるパターンが増えている点も指摘されています。

2026 年版では、画像や音声に指示を埋め込むマルチモーダル攻撃、不可視 Unicode 文字を使ったデータ持ち出し、記憶や RAG コーパスに一度書き込むと以後のセッション全てが汚染される攻撃などが新たに整理されました。

対策は「防げない」という前提に立ったアーキテクチャ側の設計が中心です。

- システムプロンプトでモデルの役割・権限を宣言的に制約する（ただし単独では不十分）
- 出力スキーマを厳格に定義し、アプリケーション側で構造的に検証する
- 認証情報や状態変更の権限はモデルではなくアプリケーションコード側に持たせ、実行時に都度検証する
- 「未検証の入力へのアクセス」「機密データへのアクセス」「外部への通信」の 3 つを同時に持つツール構成（Simon Willison が "lethal trifecta" と呼ぶ状態）は高リスクとして扱い、人間の承認を必須にする（Rule of Two）

Prompt Injection は「侵入経路」であり、侵入した後にどれだけの被害を許すかは LLM03:2026 Excessive Agency 側の対策で決まる、という役割分担が明示されています。

### LLM02:2026 Sensitive Information Disclosure

LLM を組み込んだシステムが、想定していないチャネルから機密情報を漏らしてしまう問題です。2025 年版から続けて 2 位を維持しています。

最終的な回答文だけが漏洩チャネルではない点が今回強調されています。ツール呼び出しの引数、推論過程（reasoning trace）、ログ、埋め込みベクトル、さらにはレスポンス時間やトークン長といった「観測可能な推論特性」まで、全て同じ分類・redaction ルールを適用すべき出力面として扱われます。

漏洩はモデルのライフサイクル全体で発生し得ます。

- **Training-time**: 学習データをモデルが逐語的に記憶し再現してしまう（ファインチューニング済みモデルや LoRA アダプタは特に記憶しやすい）
- **Inference-time**: システムプロンプトや RAG チャンク、他セッションのデータをその場で漏らす
- **Pipeline-time**: ファインチューニングや蒸留、合成データ生成の過程で機密データが派生物に紛れ込む
- **Observation-time**: トークン長やログ確率、キャッシュヒットの挙動など、内容そのものを受け取らなくても外部から観測できる性質から情報を推測される

対策は DSGAI（GenAI Data Security）の段階的な構造に沿って、Tier 1（全デプロイ共通の基礎対策：出所管理、コンテキストの最小化、取得前の権限チェックなど）、Tier 2（規制対象・高感度データ向けの強化：DP-SGD、ベクトルストア保護、ログ確率のゲーティングなど）、Tier 3（機密・高標的向けの高度対策：Confidential Computing、検証可能な削除、開示レッドチーミングなど）の 3 段階で整理されています。

### LLM03:2026 Excessive Agency

LLM ベースのシステムに与えられた権限が大きすぎることで、予期しない・曖昧な・操作された出力をきっかけに実害のある行動が実行されてしまう問題です。今回最も大きく順位を上げた項目（6 位 → 3 位）で、エージェント型デプロイの普及が背景にあります。

根本原因は次の 3 つに整理されています。

- **Excessive Functionality**（過剰な機能）: 読み取り専用で十分なはずのツールに削除機能まで付いている
- **Excessive Permissions**（過剰な権限）: SELECT だけで十分なはずの DB 接続に UPDATE / DELETE 権限まで付与されている
- **Excessive Autonomy**（過剰な自律性）: 高インパクトな操作を人間の確認なしに実行してしまう

対策としては「ツールを最小限にする」「ツールの機能を最小限にする」「オープンエンドなツール（シェル実行や任意 URL フェッチなど）を避け、粒度の細かいツールに置き換える」「ツールの権限を最小限にする」「ユーザーのコンテキストで実行する（委任されたスコープを保つ）」「高インパクトな操作は人間の承認を必須にする」「認可判定をモデルに委ねず、独立した Policy Decision Point で完全に仲介する」が挙げられています。可逆で低リスクな操作は自動承認し、不可逆・高リスクな操作は人間の承認に回す、というグラデーションのある運用（audit / warn / block / escalate）が現実的な落とし所として紹介されています。

なお、Excessive Agency はエージェント型システムの文脈では ASI02（Tool Misuse & Exploitation）、ASI03（Identity & Privilege Abuse）、ASI08（Cascading Failures）として、より深く扱われます。

### LLM04:2026 Supply Chain

学習データ・モデル・アダプタ・変換パイプライン・デプロイ基盤の完全性が損なわれるリスクです。2025 年版の 3 位から 4 位に順位を下げましたが、対象範囲はむしろ広がっています。

従来のソフトウェアサプライチェーンリスク（脆弱な依存パッケージ、ライセンス問題）に加え、モデル自体の供給網が主要な攻撃面として扱われるようになりました。

- 改ざんされた学習済みモデルの配布（PoisonGPT のように外見上のベンチマーク結果を保ったまま挙動を変える手法）
- モデルの出所（Provenance）を保証する仕組みの欠如（Model Card はモデルの由来を証明しない）
- LoRA アダプタや変換・マージ・量子化ワークフローの汚染（量子化後だけ悪意ある挙動を示すようフルプレシジョンモデルを作ることも可能）
- On-device（デバイス上）LLM のサプライチェーン（デバイス OS やファームウェアの脆弱性、再パッケージされたアプリ）

対策は、A06:2021（脆弱で古いコンポーネント）の考え方をモデルにも拡張する形で、サプライヤーの継続的な監査、SBOM を AIBOM（AI Bill of Materials）や ML-BOM に拡張した管理、Sigstore などによるモデルの暗号署名とその透明性ログ、モデルのマージ・変換サービスを高リスクな昇格ポイントとして監視することが挙げられています。署名は「改ざんされていないこと」の証明であって「安全であること」の証明ではない、という注意点も明記されています。

### LLM05:2026 Data and Model Poisoning

学習データやモデルの構成要素を操作し、有害な挙動・バイアス・悪用可能な弱点を埋め込む攻撃です。前バージョンの 4 位から 5 位に下がりましたが、ファインチューニングの改ざんなど新しいサブカテゴリが統合され、内容自体は拡充されています。

Pre-training、Fine-tuning、埋め込み生成、転移学習、継続学習パイプラインという LLM ライフサイクルのほぼ全段階で発生し得るのが特徴で、パラメータ数 6 億から 130 億のモデルまで、データセットの規模に関係なく **わずか 250 件の汚染文書** で裏口を作れたという研究結果も引用されています。ソフトウェアの脆弱性がパッチで直せるのに対し、汚染はデータの再検証・再学習・モデル入れ替えという高コストな対応が必要になる点が根本的な違いです。

対策は、データセットとモデルの系譜（lineage）を SBOM/ML-BOM で追跡すること、取り込むデータの厳格な検証、RAG システムの信頼境界の強制、学習損失や出力のドリフト検知、そしてアライメント後も裏口が残っている可能性を前提に、アライメントサイクルごとにトリガーを探すレッドチーミングを継続することが挙げられています。

### LLM06:2026 Unbounded Consumption

LLM への推論リクエストに対する制御が不十分なために、可用性の妨害・持続不可能なコスト・モデルの窃取（クローニング）が発生する問題です。前バージョンの 10 位（最下位）から 6 位まで、今回最も大きく順位を上げた項目の 1 つです。

コスト非対称性（攻撃者は安いコストで、システム側には不釣り合いに高いコストを発生させられる）が本質的な特徴です。extended-thinking モデルの推論トークン予算、マルチモーダル入力のトークンコスト、MCP のようなツール呼び出しプロトコルによる 1 リクエストのカスケード的な増幅など、コストが読みにくい要因が増えていることが順位上昇の背景にあります。

- **Denial of Wallet (DoW)**: 従量課金モデルを狙って高頻度のリクエストを送り、財務的な損害を与える
- **Reasoning-Loop の悪用**: 短く一見無害なプロンプトで、推論モデルを長時間・非終端のループに引き込む
- **Agent-Tool のフラッディング**: 再帰的・無限ループするツール呼び出しを誘発する悪意あるツール（例: 公開リポジトリの Claude Skill）を組み込ませる
- **エージェントセッションの肥大化**: 会話が続くほど蓄積コンテキストの再処理コストが増大し、1 リクエストあたり数十ドルにまで膨らむが、個々のリクエストはレート制限に引っかからない

対策は、トークン単位・推定コスト単位でのレート制限、上書き不能なハードな予算上限、エージェントの再帰深度・実行時間・コストに対するサーキットブレーカー、推論基盤（vLLM、TensorRT-LLM など）自体の堅牢化が挙げられています。

### LLM07:2026 Misinformation

LLM が、人間の判断・自動ワークフロー・エージェントの行動に影響を与えるほど信憑性のある誤った情報や不完全な情報を生成する問題です。前バージョンの 9 位から 7 位に上昇しました。

ハルシネーション、古い・不完全なコンテキスト、根拠の乏しさ、偏った・破損したデータ、誤解を招く要約、未検証のツール出力など発生源は多岐にわたり、攻撃者が意図的に誘発することもあります。現代のシステムではモデルの出力がそのままツール呼び出しや状態推論、承認判断に使われるため、単なる「間違った答え」がそのまま「間違った行動」に変換されてしまう点がシステムレベルの問題として扱われています。流暢で自信のある出力を人間もシステムも権威あるものとして扱ってしまう **Overreliance** がこの失敗モードの中核です。

対策として、「Claim-Check-Act パターン」（生成と実行を分離し、行動前に主張を検証する）や、確信度だけでなく根拠との整合性（Groundedness）や一貫性を検証シグナルとして使うこと、ツール呼び出し前に引数・権限・前提条件・現在の状態を検証すること、高インパクトな行動には承認ワークフローとシステムチェックを設けることが挙げられています。

### LLM08:2026 Hidden Context Exposure

モデルのコンテキストに置かれた、ユーザーには見えないはずのシステム指示や運用上の情報が、不正に抽出・推測・再構築される問題です。前バージョンの System Prompt Leakage（7 位）を改名・再定義したもので、対象範囲がシステムプロンプトだけでなく、RAG から取得されたポリシー文書、モデルに提示されるツール・関数のスキーマ、その他モデルの振る舞いを規定する材料全般に広がっています。

重要な前提として、「隠されたコンテキストはいつか露見するものとして設計すべき」という原則が明記されています。認証情報や接続文字列を隠しコンテキストに埋め込まない、隠しコンテキストの秘匿性そのものを権限分離やコンテンツフィルタリングの唯一の防衛線にしない、という考え方です。深刻度は、機密情報がない informational から、内部ルールや役割定義が露出する medium、認証情報が埋め込まれている high、そこから RCE やデータ全体の持ち出しにつながる critical まで段階的に評価します。

このリスクは単独でも問題ですが、他のリスクを増幅する性質を持ちます。露出したルールがより的確な Prompt Injection（LLM01）を可能にし、埋め込まれた認証情報がそのまま Sensitive Information Disclosure（LLM02）になり、露出したツールの権限情報が Excessive Agency（LLM03）の攻撃対象選定に使われ、出力フォーマットのルール露出が Improper Output Handling（LLM10）を助けるという形です。対策は、機密データを隠しコンテキストに置かないこと、モデル行動の制御をハードコードされた決定的な仕組みで行うこと、認可判定をモデルから独立させることの 3 点に集約されています。

### LLM09:2026 Vector and Embedding Weaknesses

テキスト・画像・コード・音声を数値表現（埋め込みベクトル）に変換し、類似検索でモデルに何を見せるかを決める仕組みに存在するリスクです。前バージョンの 8 位から 9 位に順位を下げましたが、内容としては Prompt Injection とは明確に異なる、独立したリスクとして扱われています。

「汚染はシステムを誤らせ、逆変換（inversion）は情報を漏らし、ジャミングはシステムを黙らせ、アクセス制御の失敗はシステムを無差別にする」という整理が本文中で示されています。

- **クロステナント漏洩**: マルチテナント環境で、アクセス制御がかかる前に類似検索がインデックス全体を走査してしまい、結果件数やスコア分布から他テナントの文書の存在や内容を推測できる
- **埋め込みの逆変換（Inversion）**: 保存された埋め込みベクトルから元のテキストを 50〜92% 程度の精度で復元できる。差分プライバシーのノイズを加えても効果を発揮する手法も報告されている
- **Retrieval-Time Poisoning**: 攻撃者が書き込めるコーパスに、対象クエリの埋め込み近傍に着地するようなコンテンツを混入させる
- **Retrieval Jamming**: 悪意ある指示を含まない「ブロッカー文書」を使って、RAG システムを可用性攻撃で沈黙させる
- **Membership Inference**: 特定の文書（医療記録など）がインデックスに存在するかどうか自体をスコアから推測する
- **Semantic Cache / 重複除去の汚染**: 類似度の閾値付近を狙ってキャッシュを汚染し、攻撃者のコンテンツを大量の類似クエリに配信させる
- **マルチモーダル埋め込みの汚染**: CLIP のようなクロスモーダルエンコーダを狙い、人間には無害に見える画像にテキストクエリへの汚染を仕込む

最も重要な注意点は「埋め込みだけの漏洩」を安全とみなしてはいけないということです。埋め込みは元の文書と同じ機密度で扱うべきで、GDPR 等の通知義務の判断でも「埋め込みだけの流出」を低リスクと再分類してしまうのは誤りだと明記されています。対策は、テナントのスコープをインデックスクエリ内部で強制すること（後付けのフィルタでは不十分）、埋め込み前のコンテンツ正規化と出所管理、信頼レベルごとのインデックス分離、生の類似度スコアをクライアントに返さないことなどが挙げられています。

### LLM10:2026 Improper Output Handling

LLM が生成した出力を下流のコンポーネントに渡す前の検証・サニタイズが不十分な問題です。前バージョンの 5 位から 10 位まで、今回最も大きく順位を下げた項目です。

LLM が生成するコンテンツは間接的にユーザーが制御できる入力と同じものだという前提（ゼロトラスト）に立つ必要があります。過剰な権限を持つ LLM、Indirect Prompt Injection への脆弱性、サードパーティツールからの未検証入力、コンテキストに応じた出力エンコードの欠如などが組み合わさると影響が拡大します。

- LLM 出力を `exec` や `eval` に直接渡してしまい RCE に至る
- LLM が生成した JavaScript や Markdown がそのままブラウザで解釈され XSS になる
- LLM 生成の SQL がパラメータ化されずに実行され SQL インジェクションになる
- 出力中の ANSI エスケープシーケンスがターミナルやログビューアで解釈され、視覚的なスプーフィングやクリップボードハイジャック（OSC 52）を引き起こす
- チャット UI が出力内の Markdown 画像や リンクプレビューを自動でレンダリングし、画像 URL のホスト名やクエリ文字列経由で会話データが持ち出される

対策は Web アプリケーションの入力検証と同じ発想を出力側に適用することです。コンテキストに応じた出力エンコード（HTML エンコード、JavaScript エンコードなど）、データベース操作へのパラメータ化クエリの徹底、厳格な Content Security Policy、制御文字のサニタイズ、そしてチャット UI・IDE・メールクライアントなど「出力を自動でレンダリングするクライアント」側で外部リソースへの自動フェッチを許可リスト方式に制限することが挙げられています。

## まとめ

OWASP Top 10 for LLM Applications 2026 を通読して感じたのは、Letter from the Project Leads の冒頭にある一文がリスト全体の思想を最も端的に表しているという点です。

> Stop trying to build a model that cannot be fooled. Build the system around it, so that when the model is fooled, and it will be, nothing important breaks.

モデルを騙されないように作ることをやめ、いつか騙されることを前提にシステム全体を設計するという姿勢が、Prompt Injection の「防げないから境界を制約する」という対策方針から、Hidden Context Exposure の「隠しコンテキストはいつか露見するものとして扱う」という原則まで、一貫して流れています。

今回追加された Appendix A では、10 個のリスクそれぞれが ASI（Agentic Top 10）、DSGAI（GenAI Data Security）、MITRE ATLAS、MITRE ATT&CK、CWE、NIST AI 600-1 / AI RMF、CSA AICM、OWASP AIVSS という 9 つの外部フレームワークとどう対応するかがマッピングされています。ガバナンスやコンプライアンスの文脈でこのリストを使う場合には、この対応表が実務上かなり役立つはずです。

また、この記事では「モデルがアプリケーションの一部品として動く」ケースを中心に扱いましたが、モデルがツールを自律的に呼び出し、記憶を持ち、その結果が連鎖的に他のシステムへ広がる「エージェント」としての振る舞いが関わる場合は、姉妹プロジェクトの OWASP Top 10 for Agentic Applications と組み合わせて読むことが推奨されています。どちらか一方だけでは、その境界にあるリスクを見落としてしまうためです。

この記事がどなたかの役に立つと嬉しいです。
