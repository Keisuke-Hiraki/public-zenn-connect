こんにちは、CSC の [CloudFastener](https://cloud-fastener.com/) というプロダクトで TAM のポジションで働いている平木です！

同じ「インターネットから到達可能で、悪用可能な脆弱性を持つ EC2 インスタンス」でも、決済処理を担う本番サーバーと検証用に放置されたサンドボックスとでは、対応の緊急度がまったく違います。
ところが、これまでの Security Hub の Exposure finding は、この「ビジネス上どれだけ大事なリソースか」を明示的に扱う仕組みを持っていませんでした。

2026 年 10 月 14 日、AWS Security Hub にリソースの重要度（Criticality）が追加され、Exposure finding の優先度付けに使われるようになりました。

https://aws.amazon.com/jp/about-aws/whats-new/2026/10/security-hub-resource-criticality/

この記事では、リソースの重要度がなぜセキュリティ運用の判断材料として大事なのかを整理したうえで、今回のアップデートで何ができるようになったのかを紹介します。

:::message
この記事の 3 行まとめ

- Security Hub のリソースに `Very High` / `High` / `Medium` / `Low` / `Unknown` の 5 段階の重要度が付くようになりました。この重要度は Exposure finding の影響度（Impact）と深刻度の計算に使われます
- 重要度はリソース名とタグから自動で推論され、自動化ルール（リソースルール）で明示的に上書きできます
- 追加料金や有効化の操作は不要で、すべての Security Hub ユーザーが利用できます
:::

アップデート前後の違いを先にまとめておきます。

| 項目 | これまで | アップデート後 |
| --- | --- | --- |
| リソースの重要度 | なし | 5 段階（`Very High`〜`Unknown`）でリソースごとに付与 |
| 重要度の決まり方 | - | リソース名・タグからの自動推論、または自動化ルールでの明示設定 |
| 自動化ルールの種類 | 検出結果を更新する「検出結果ルール」のみ | 重要度を設定する「リソースルール」が追加 |
| Exposure の深刻度 | 悪用のしやすさ（Likelihood）と影響度（Impact）で決定 | 影響度の計算に、リソースの重要度が入力として加わる |
| コンソール表示 | - | 「リソース」ページの「重要度」列（並べ替え・フィルター・グループ化）、Exposure finding の「リソース」タブ |
| 料金・有効化 | - | Security Hub Essentials に含まれ追加料金なし。常に有効 |

## リソースの重要度はなぜセキュリティ運用で大事なのか

アップデートの中身に入る前に、そもそもなぜ「リソースの重要度」がセキュリティ運用の判断材料として欠かせないのかを整理します。

### 深刻度だけでは「どれから直すか」が決まらない

セキュリティのリスクは、一般に「起こりやすさ」と「起きたときの影響の大きさ」の組み合わせで評価します。
CVSS や Security Hub の Severity はよくできた指標ですが、多くは脆弱性や設定ミスそのものの性質、つまり起こりやすさの側を表しています。

一方で、同じ脆弱性が見つかったときに実際の被害がどれだけ大きくなるかは、そのリソースが何を担っているかで決まります。
顧客の個人情報が入ったデータベースにつながる本番サーバーと、誰も使っていない検証環境のサーバーでは、同じ CVE でも事業へのダメージがまるで違います。

CloudFastener でお客様のセキュリティ運用を支援していると、「Critical や High の検出結果が数百件あって、どれから手を付けるべきか分からない」というご相談をよくいただきます。
このとき実際に優先順位を決める手がかりになるのは、深刻度そのものよりも「このアカウントは本番か」「このバケットには何が入っているか」といった、リソースのビジネス上の位置づけであることがほとんどです。

### これまでは人の頭の中にしかなかった情報

問題は、この「ビジネス上の重要度」がこれまで Security Hub の外側にしかなかったことです。

多くの組織では、本番かどうかはアカウント名やタグの命名規則で表現し、重要なシステムの一覧は CMDB やスプレッドシートで管理しています。
検出結果のトリアージでは、担当者がその情報を頭の中で突き合わせながら優先度を判断していました。
これでは担当者の経験に判断が依存しますし、リソースが数千、数万になると突き合わせ自体が追いつきません。

今回のアップデートで、この重要度が Security Hub の中のデータになりました。
しかも単なるラベルではなく、Exposure finding の深刻度の計算に組み込まれます。
**重要度を正しく設定しておけば、Security Hub が出してくる優先順位そのものが自社のビジネスの実態に近づく**、というのが今回のアップデートのいちばん大きな意味だと思います。

## 今回のアップデートでできるようになったこと

ここからは、今回のアップデートで何ができるようになったのかをドキュメントに沿って説明します。

https://docs.aws.amazon.com/securityhub/latest/userguide/resources-adv.html

### リソースごとに 5 段階の重要度が付く

このセクションでは、重要度として取りうる値を確認します。

重要度は「そのリソースがビジネスにとってどれだけ重要か」を表す値で、次の 5 段階です。

| 値 | 意味 |
| --- | --- |
| `Very High` | 最も重要 |
| `High` | 重要 |
| `Medium` | 中程度 |
| `Low` | 重要度が低い |
| `Unknown` | 判定できていない（深刻度の計算に影響しない） |

`Unknown` は「重要度が低い」という意味ではなく、「判断材料がない」という意味です。
後述するとおり、`Unknown` のリソースは Exposure finding の深刻度に影響しません。

重要度は、Security Hub コンソールの「リソース」ページに「重要度」列として表示され、並べ替え・フィルター・グループ化に使えます。

![「リソース」ページの重要度列とクイックフィルター](/images/Screenshot_2026-10-16_at_12-58-59.png)

### リソース名とタグから自動で推論される

このセクションでは、何も設定しなくても重要度が付く仕組みを説明します。

Security Hub は、デフォルトで次の 2 つの手がかりから重要度を推論します。

- **リソース名**：名前に含まれるパターンを見ます。たとえば名前に `pci` や `prod` を含むリソースは、`sandbox` という名前のリソースより重要と判定されます
- **タグ**：タグに含まれるパターンを見ます。たとえば `environment=production` のタグを持つリソースは、`environment=dev` のリソースより重要と判定されます

どの手がかりで重要度が決まったのかは記録されていて、API では `CriticalitySources` として、ソース（`ResourceName` / `TagInference` / `AutomationRule`）と理由を確認できます。

推論は名前やタグに含まれるキーワードをもとにしているため、命名規則によっては実態とずれた重要度が付くこともあります。
たとえば、本番のリソースでも名前に `test` を含んでいると、重要度が低く判定される可能性があります。
重要なリソースについては、次に紹介する自動化ルールで明示的に設定しておくのが安心です。

### 自動化ルール（リソースルール）で重要度を明示的に設定できる

このセクションでは、重要度を自分で設定する方法を説明します。

自動推論の結果は、Security Hub の自動化ルールで上書きできます。
今回のアップデートで、自動化ルールは 2 種類になりました。

https://docs.aws.amazon.com/securityhub/latest/userguide/securityhub-v2-automation-rules.html

| ルールの種類 | 条件の対象 | できること |
| --- | --- | --- |
| 検出結果ルール（finding rule） | 検出結果の OCSF フィールド | 深刻度・ステータス・コメントの更新、Jira Cloud / ServiceNow ITSM のチケット作成 |
| リソースルール（resource rule） | リソースの属性 | リソースの重要度の設定 |

リソースルールの条件には、リソース ID・リソース名・リソースタイプ・アカウント ID・リージョン・Organizations の組織 ID・タグなどを使えます。
たとえば「特定アカウントのコンピューティングリソースをすべて `Very High` にする」「`environment=production` タグを持つリソースを `High` にする」といった設定ができます。

運用上押さえておきたい点は次のとおりです。

- 自動化ルールで設定した重要度は、自動推論より常に優先されます
- 同じリソースに複数のリソースルールが一致した場合、最後に適用されたルール（ルール順序の数値が大きいほう）の値が最終的な重要度になります
- 検出結果ルールは作成後に新規作成・更新された検出結果だけが対象ですが、リソースルールは **すでにインベントリにあるリソースと、今後検出される新しいリソースの両方** に適用されます
- 1 つのルールに検出結果の条件とリソースの条件は混在させられません
- 検出結果ルールとリソースルールは同じクォータを共有し、アカウント・リージョンあたり合計 100 個までです
- リージョン集約を使っている場合、ルールはホームリージョンでのみ作成でき、リンクされたリージョンすべてに適用されます
- セルフホスト型の AI リソースはリソースルールの対象外で、引き続き自動推論の重要度が使われます

### Exposure finding の深刻度に重要度が反映される

このセクションでは、重要度が Exposure finding の深刻度にどう効いてくるのかを説明します。

Exposure finding の深刻度は、悪用のしやすさを表す **Likelihood** と、悪用されたときの被害の大きさを表す **Impact** の 2 軸で決まります。
Likelihood がベースの深刻度を決め、Impact によって最大 1 段階上下します。

https://docs.aws.amazon.com/securityhub/latest/userguide/exposure-findings-severity.html

| Likelihood ＼ Impact | Low | Medium | High |
| --- | --- | --- | --- |
| Very High | HIGH | CRITICAL | CRITICAL |
| High | MEDIUM | HIGH | CRITICAL |
| Moderate | LOW | MEDIUM | HIGH |
| Low | INFORMATIONAL（公開されない） | LOW | MEDIUM |

Impact は、リソースに紐づく IAM プリンシパルの実効的なアクセス許可から、攻撃者がたどり着けるリソース（影響範囲）を分析して算出されます。
今回のアップデートで、この Impact の計算に **主要リソースの重要度** が入力として加わりました。

https://docs.aws.amazon.com/securityhub/latest/userguide/exposure-findings-supported-traits.html

表を見ると、同じ Likelihood が `High` でも、Impact が `Low` なら `MEDIUM`、`High` なら `CRITICAL` と 2 段階の差がつきます。
重要度は Impact の入力の 1 つなので、重要度だけで深刻度が決まるわけではありません。
それでも、本番の基幹リソースと検証環境のリソースとで Exposure の並び順に差をつけられるようになったのは大きな変化です。

なお、`Unknown` のリソースは深刻度に影響しません。
また、Impact は深刻度を調整するだけで、重要度や Impact だけを理由に Exposure finding が新たに生成されることはありません。

Exposure finding の詳細画面では、「リソース」タブでプライマリリソースの重要度を確認できます。

![Exposure finding の「リソース」タブに表示されたプライマリリソースの重要度](/images/Screenshot_2026-10-16_at_13-01-40.png)

## まとめ

Security Hub にリソースの重要度が追加され、Exposure finding の深刻度の計算に「そのリソースがビジネスにとってどれだけ大事か」が反映されるようになりました。

これまで担当者が頭の中で行っていた「この検出結果は本番だから急ぐ」「これは検証環境だから後回し」という判断を、Security Hub の中のデータとして持てるようになったのが今回のポイントです。
重要度はリソース名やタグから自動で推論されますが、`Unknown` のリソースは深刻度に影響しないため、守りたいリソースは自動化ルールで明示的に設定しておくのがおすすめです。

追加料金も有効化の操作も不要なので、まずは「リソース」ページで自分の環境のリソースにどんな重要度が付いているかを確認するところから始めてみてください。
